# 0011 — Identity and RBAC

Status: accepted (2026-11-01)

## Principals

| Principal | How it's verified | Notes |
|---|---|---|
| owner | The bootstrap bearer token | Implicit cluster-admin; break-glass use. Its writes are audited as `owner`. |
| node | mTLS client certificate | Limited to the node API, as before. |
| ServiceAccount | `clk_…` API token | Stored as a SHA-256 hash and shown once. Optional TTL; revocable. Deleting the account disables its tokens. |
| OIDC user | ID token presented as the bearer | Checked against the issuer's discovery document and JWKS: `iss`, `aud`, `exp` and `nbf`. Asymmetric algorithms only. A token with `email_verified: false` is refused. The user claim defaults to `email` and the groups claim to `groups`. |

## Roles and bindings

- **Roles:** fixed built-ins: `viewer`, `editor`, `approver`, `admin` and `cluster-admin`. Their permission sets are defined in `clankr_types::rbac`.
- **Bindings:** a `RoleBinding` names the role and its subjects (`user:`, `group:` or `serviceaccount:ns/name`).
  - A binding in namespace X applies only to X.
  - A binding in `clankr-system` applies cluster-wide. It is the only way to get the cluster-scoped routes: node maintenance, audit, and listing across namespaces.
- **Escalation:** a namespace admin can't escalate out of their namespace, because writing bindings in `clankr-system` needs RbacWrite there.

## Enforcement

- **Single check point:** `rbac::required(method, path)` maps every route to a namespace and a permission. Unknown routes need cluster-admin, so the check is deny by default.
- **Denials:** a denial returns 403 and is written to the hash-chained audit log with its reason. An invalid credential returns 401 and is audited the same way.

## Follow-ups (same milestone)

- **Binding cache:** RoleBindings are cached with the resource revision they were read at. Each request reads only the revision row and re-lists bindings after any resource write, so a deleted binding stops working on the very next request.
- **IdP key rotation:** an unknown `kid` refetches the JWKS, at most once per `min_refresh` (30 s). If a refresh fails, the last good keys stay in use.
- **CLI login:** `clank login` uses the OIDC device flow (RFC 8628) and saves `~/.config/clankr/session.json` (0600). The ID token is refreshed silently with the refresh token, and a rotated refresh token is persisted. `CLANKR_TOKEN` overrides the session, and the session overrides the owner token file.

**Not yet:** custom roles.
